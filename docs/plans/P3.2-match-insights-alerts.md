## 1. Goal and acceptance criteria

1. Every scored job shows a **match breakdown**:
   - skills matched X of Y, with the matched and missing lists;
   - title fit;
   - seniority fit (match / stretch / overqualified);
   - up to 3 important skills the job requires that the resume lacks.
2. Every job shows **freshness**: "posted 5 h ago", an **Early** badge (under 24 h), and "new since your last search".
3. A user can save up to N **job alerts** (search profile + time of day + minimum score). Each day the alert runs, and new matches above the minimum score arrive as an **email digest** and in an in-app list. A job is never sent twice.
4. **HN "Who is hiring?"** jobs appear for remote searches. They are parsed without AI, filtered by region, and link to the HN comment.
5. **Applicant count** ("143 applicants") is shown on LinkedIn jobs that reach the feed.
6. **Google Jobs** results come in through the user's own free Bright Data, SerpApi or JSearch key. The Muse runs with a free key if that clears the block.
7. The profile stores **relocation** preferences and **EEO answers** (default "prefer not to say") for P4 forms. EEO answers never go to an AI model.
8. Offline tests cover all of the above; the existing 173 tests stay green.

## 2. Design

### 2.1 Match breakdown
- **Deterministic part (free, no AI):**
  - `skills_matched` / `skills_missing` / `skills_total`: from the search profile's weighted skills, synonyms included. This reuses `search_profiles.skill_terms` / `weighted_keyword_score`, which already does the matching.
  - `title_fit` (0–100): token overlap with the profile's target titles.
- **AI part (about 30 extra output tokens per job):** the scoring JSON gains:
  - `seniority`: `match | stretch | overqualified`
  - `missing_required`: up to 3 skills the job requires that the resume doesn't show

  If a model leaves these out, the job still gets its score. The breakdown is shown as partial.
- **Storage:** stored in `user_jobs.breakdown` (JSON). It goes out in the feed payload (`match` field) and in `GET /jobs`. Re-shown jobs (`include_seen`) reuse it without calling the AI again.
- **Legacy mode** (no search profile): skills come from `score.skills`, and title fit from `career_targets`.

### 2.2 Freshness
- **New column `jobs.posted_at`:** parsed once from the `posted` text (same parser as the P3.1 adapters). The migration backfills existing rows where it can.
- **Computed fields:** the feed and `GET /jobs` gain `posted_at`, `posted_hours_ago`, `early` (under 24 h) and `new_since_last_search` (the job's `first_seen_at` is after the user's previous run).
- **Applicant count:** see 2.5.

### 2.3 Job alerts
- **Tables:**
  - `job_alerts`: user_id, name, search_profile_id, `hour_local` + `timezone` (default Asia/Kolkata), `min_score` (default 75), enabled, last_run_at, next_run_at. Limit `JOB_ALERTS_MAX_PER_USER` (3).
  - `job_alert_runs`: alert_id, started/finished, counts, `job_ids` (JSON), emailed_at, error.
- **API:**
  - `GET/POST/PUT/DELETE /alerts`
  - `POST /alerts/{id}/run-now` (rate-limited)
  - `GET /alerts/{id}/runs`
  - `GET /alerts/runs/{run_id}/jobs`
- **Scheduler:** a Celery **beat** process ticks every 10 minutes on the `maintenance` queue (blueprint §10). The tick dispatches due alerts, using a row-level "claim" so two beats can't run the same alert.
- **Each alert run** is one task on the default queue:
  - it builds params exactly like `build_pipeline_params` with the alert's search profile;
  - it runs search → dedupe → filters → seen-skip → score through the existing `_process_job` path, so it costs the same per job as a manual run and never re-scores seen jobs;
  - it keeps jobs ≥ `min_score` that the user has never been shown.
- **Delivery:** results are saved in `job_alert_runs`. When the run has new jobs, a plain-text email digest goes out (title, company, score, one-line reason, link) through the existing email provider (`EMAIL_BACKEND`; the console backend in dev). Each job appears in at most one digest; this relies on `user_jobs` "seen".
- **Gating:** new entitlement `job_alerts` (on by default, `quota_per_day` = number of alert runs). The admin kill switch and a disabled user stop alerts at once (P1 rules).

### 2.4 HN "Who is hiring?" source (`hn_hiring`, kind `feed`)
- **Fetch:**
  1. find this month's thread with Algolia (`search_by_date?tags=story,author_whoishiring`, title starts with "Ask HN: Who is hiring?");
  2. fetch `items/{id}` and read the top-level comments only.
  - Cached for 6 hours (the thread changes slowly), through the P3.1 feed cache.
- **Parse:** the header line splits on `|` (or " – " / " — "):
  - company is the first part;
  - title is the part with role words;
  - location / remote is the part with REMOTE, ONSITE, a city or a country;
  - the rest of the comment is the description.

  Posts without a parseable header are skipped (about 12% this month). The URL is `https://news.ycombinator.com/item?id={comment}`.
- **Region and ranking:** the region comes from text like "Remote (US)" / "REMOTE (Germany)" and goes through the existing `geo_allows`. Rank: aggregator. ToS risk: none (public API).
- **Defaults:** on by default, remote searches only, like the other feeds.

### 2.5 Applicant count (free, LinkedIn only)
- **Where it comes from:** LinkedIn's public job page (`/jobs-guest/jobs/api/jobPosting/{id}`) shows "143 applicants" / "Over 200 applicants". Live-checked 2026-10-16 on 3 of 3 jobs. JobSpy already loads this page for descriptions but discards the count.
- **When we fetch it:** only for LinkedIn jobs that **pass scoring** (i.e. are shown). At most `APPLICANT_COUNT_MAX_PER_RUN` (20), paced 2–4 s apart.
- **Storage:** `jobs.applicants` (text as shown, e.g. "Over 200") + `jobs.applicants_checked_at`. Re-checked at most every 24 h.
- **Risk:** same ToS risk as the existing LinkedIn source (scraping). Off when LinkedIn is paused or disabled. On 429 or an empty page, it stops for the run.
- **Other sources:** Indeed, Naukri, ATS boards and the APIs don't publish a count, so their jobs show nothing rather than a guess.

### 2.7 Apply-profile fields (for P4 forms)
- **Relocation:** `applicant_info.willing_to_relocate` (yes / no / depends), `relocation_locations` (list), `requires_sponsorship` (bool) in `PUT /profile`.
- **EEO / diversity answers:**
  - `applicant_info.eeo` = gender, ethnicity/race, veteran status, disability status, pronouns.
  - Every one defaults to "prefer not to say". All optional.
  - The resume parser never fills them (only the user does).
  - **Never sent to an AI model or a log.** Encrypted at rest with the same envelope scheme as keys.
  - The UI explains these are only used to answer optional employer questions.

## 4. Risks

| Risk | Mitigation |
|---|---|
| Alerts multiply AI cost (daily runs per user) | Seen jobs are never re-scored; keyword prefilter before the AI; per-user alert limit and daily quota; Free-tools-only still applies to models |
| LinkedIn rate limits from unattended daily runs | Alerts are spread over the hour (random minute offset); existing pacing/retries; the source breaker pauses LinkedIn if it starts failing |
| Beat runs twice (two processes) | Alert claim = conditional UPDATE on `next_run_at`, so only one wins |
| Email deliverability | Uses the same SMTP setup as OTP; the digest is plain text with an unsubscribe-style "turn off this alert" link to the app |
| HN header formats vary | Unparseable posts are skipped, not guessed; the parser is tested on recorded real comments |
